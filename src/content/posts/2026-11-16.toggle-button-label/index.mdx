화상회의 중에 옆자리 동료가 말을 걸어왔다. 대답하기 전에 먼저 마이크 버튼을 한 번 본다.
버튼에는 마이크에 사선이 그어진 음소거 표시가 나타난다. 이 표시는 음소거가 된 상태일까, 아니면 누르면 음소거가 된다는 뜻일까?

버튼은 하나인데 읽는 방법이 두 가지라서 생기는 일이다.
서비스를 디자인하거나 개발하다 보면 한 번쯤 이 논쟁에 빠진다.
**"토글 버튼은 현재 상태를 표현해야 하는가, 누르면 실행될 미래의 동작을 표현해야 하는가?"**

단순해 보이지만 사용자가 헷갈리느냐 마느냐를 좌우하는 중요한 문제다.
이 질문에 답할 수 있는 기준과 사례를 정리해 본다.

## 버튼 하나가 두 가지 일을 맡아서 생기는 혼선

'저장'이나 '다운로드'처럼 상태가 남지 않는 버튼은 누르면 일어날 일만 표현하면 된다.
반면 누를 때마다 두 상태를 오가는 토글 버튼은 버튼 하나가 두 가지 일을 한꺼번에 맡는다.
하나는 **지금 어떤 상태인가**를 알리는 일이고, 다른 하나는 **누르면 무슨 일이 일어나는가**를 알리는 일이다.

<ruby>앨런 쿠퍼<rt lang="en">Alan Cooper</rt></ruby>는 저서 『About Face』에서 이런 버튼을 <ruby>플립플롭<rt lang="en">Flip-flop</rt></ruby> 버튼이라 부르며 피해야 할 방식으로 꼽는다.
모든 컨트롤에는 현재 상태를 사용자에게 알릴 의무가 있는데, 플립플롭 버튼은 이 의무를 다하지 못한다는 것이다.
버튼은 상태를 알리는 표시가 될 수도 있고 상태를 바꾸는 명령이 될 수도 있지만, 둘을 한꺼번에 할 수는 없다.

닐슨 노먼 그룹의 <ruby>라루카 부디우<rt lang="en">Raluca Budiu</rt></ruby>도 [음소거 버튼을 다룬 글](https://www.nngroup.com/articles/state-switch-buttons/)에서 같은 문제를 짚는다.
두 상태를 오가는 컨트롤은 현재 상태와 누르면 옮겨 갈 상태를 모두 분명하게 전해야 하는데,
음소거 버튼에서는 지금 상태가 무엇이고 무엇으로 바뀌는지를 사용자가 쉽게 알 수 없다고 한다.

## 미래 동작만 표현해도 되는지 가르는 세 가지 질문

그렇다면 버튼 하나가 둘 중 하나만 표현할 수 있을 때 무엇을 골라야 할까.
부디우는 버튼이 누르면 일어날 일만 표현해도 사용자가 현재 상태를 놓치지 않는지 따져 보는 세 가지 질문을 제시한다.

### 1. 버튼 밖에서 현재 상태를 알 수 있는가?

동영상 플레이어의 재생 버튼을 보자. 영상이 멈춰 있을 때 ▶가 보이고, 재생 중일 때는 ❚❚가 보인다.
버튼은 지금 상태가 아니라 누르면 일어날 일만 표현하지만 아무도 헷갈려하지 않는다.
화면이 움직이고 소리가 들리니, 재생 중이라는 사실은 버튼을 보지 않아도 알 수 있기 때문이다.

음소거 버튼은 반대다. 내 마이크가 켜져 있는지는 화면 어디에도 보이지 않고 귀로도 들리지 않는다.
상태를 알려주는 자리가 버튼 하나뿐인데 그 버튼이 모호하면 글머리의 상황이 벌어진다.

| 버튼 | 버튼 밖의 단서 | 버튼이 표현할 것 |
| --- | --- | --- |
| 재생 / 일시정지 | 화면이 움직이고 소리가 난다 | 미래 동작 |
| 펼치기 / 접기 | 내용이 펼쳐져 있다 | 미래 동작 |
| 전체 화면 | 화면이 가득 차 있다 | 미래 동작 |
| 마이크 음소거 | 없다 | 현재 상태 |
| 좋아요, 북마크 | 없다 | 현재 상태 |
| 굵게(**B**) | 없다. 커서만 놓인 자리의 서식은 보이지 않는다 | 현재 상태 |

단서가 있으면 버튼은 미래 동작만 표현해도 된다. 부디우는 누르면 옮겨 갈 상태를 표현하는 쪽을 버튼 디자인의 표준 권고라고 부른다.
단서가 없으면 버튼이, 또는 버튼 바로 곁의 무언가가 현재 상태를 표현해야 한다.

새로운 기준은 아니다. <ruby>제이콥 닐슨<rt lang="en">Jakob Nielsen</rt></ruby>의 사용성 휴리스틱 첫 번째가 <ruby>시스템 상태의 가시성<rt lang="en">Visibility of System Status</rt></ruby>이다.
지금 무슨 일이 일어나고 있는지를 시스템이 사용자에게 늘 알려야 한다는 원칙이다.
상태가 보이지 않아서 생기는 실수는 <ruby>모드 오류<rt lang="en">Mode Error</rt></ruby>라는 이름으로 오래 연구되어 왔다.
<ruby>셀런<rt lang="en">Sellen</rt></ruby>, <ruby>커텐바흐<rt lang="en">Kurtenbach</rt></ruby>, <ruby>벅스턴<rt lang="en">Buxton</rt></ruby>의 1992년 실험에서는 현재 모드를 눈이나 몸으로 느끼게 해 주는 피드백이 모드 오류를 줄였다.

아래 데모에서 두 버튼을 눌러 보자. 둘 다 같은 규칙으로, 누르면 일어날 일만 표현한다.
재생 버튼은 영상이 움직이는지만 봐도 지금 상태를 알 수 있다.
음소거 버튼은 몇 번을 눌러도 지금 마이크가 켜져 있는지 확신하기 어렵다.
**마이크 상태 표시 붙이기**를 켜서 버튼 밖에 단서를 만들어 주면 같은 버튼이 곧바로 읽힌다.

### 2. 반대 상태가 뻔한가?

버튼이 미래 동작만 표현하려면 사용자가 반대쪽 상태를 스스로 떠올릴 수 있어야 한다.
재생의 반대는 일시정지이고 펼치기의 반대는 접기다. 관습이 굳어 있어서 한쪽만 봐도 다른 쪽을 안다.
부디우는 반대 상태가 뻔하지 않다면 상태 표시와 전환 버튼을 따로 두라고 권한다.

상태가 셋 이상이면 이 조건은 아예 성립하지 않는다. 보기 방식이 카드형, 리스트형, 갤러리형으로 돌아간다면
지금 방식을 표현한 버튼은 누르면 어디로 가는지 알려주지 못한다. 이때는 선택지를 모두 보여주는 편이 낫다.

아래 데모는 세 가지 보기 방식을 오가는 버튼을 세 가지로 표현한 것이다.
다음 방식을 표현한 버튼은 화면을 봐야 지금 방식을 알 수 있고, 지금 방식을 표현한 버튼은 누르면 어디로 가는지 알려주지 못한다.
**미리보기 가리고 버튼만 보기**를 켜면 차이가 더 분명해진다.
지금 어떤 방식인지와 누르면 어떤 방식이 되는지를 모두 맞힐 수 있는 건 선택지를 전부 보여주는 세그먼트뿐이다.

### 3. 상태를 빨리 확인하고 바꿔야 하는가?

버튼이 미래 동작만 표현하면 사용자는 현재 상태를 거꾸로 짐작해야 한다. 부디우는 어떤 추론이든 시간과 인지적 노력이 든다고 지적한다.
회의 중에 질문을 받고 급히 음소거를 풀어야 하는 사람에게는 인터페이스를 두고 따져 볼 시간이 없다.
이런 경우라면 상태를 알려주는 아이콘과 상태를 바꾸는 버튼을 따로 두라는 것이 그의 권고다.

## 현재 상태를 표현하는 방법

세 질문 가운데 하나라도 걸린다면 현재 상태를 표현할 방법을 찾아야 한다. 방법은 네 가지다.

### 켜진 모양으로 표현하기

버튼의 표현은 하나로 고정하고, 켜짐과 꺼짐을 버튼의 모양으로 표현한다.
문서 편집기의 굵게(**B**) 버튼은 글자가 늘 **B**이고, 켜져 있는 동안 배경색이 채워진다.
단, 비교할 옆 버튼이 없으면 어느 쪽이 켜진 모양인지 사용자가 기억해야 한다.

<StateMethodDemo method="filled" />

### 상태와 동작을 나누어 표현하기

부디우가 가장 안전하다고 꼽는 방법이다. 현재 상태를 알리는 요소와 상태를 바꾸는 요소를 따로 둔다.
[Zoom](https://www.zoom.com/)의 음소거 컨트롤은 이 둘을 한 자리에 묶었다. 아이콘은 현재 상태를, 그 아래 글자는 누르면 일어날 일을 표현한다.
글머리의 마이크 버튼에 필요했던 것이 이것이다.

<StateMethodDemo method="split" />

### 글자는 동사로 끝내기

쿠퍼도 버튼에 동작을 동사구로 풀어 쓰라고 권한다. 한국어에서는 특히 '음소거 해제'처럼 명사로 끝내면
지금 해제된 상태인지, 누르면 해제하겠다는 건지 여전히 알 수 없다.
'음소거 해제하기', '카드형으로 보기'처럼 동사로 끝내야 누르면 일어날 동작으로 읽힌다.

<StateMethodDemo method="verb" />

### 선택지를 모두 보여주기

쿠퍼가 플립플롭 버튼의 대안으로 드는 것이 라디오 버튼 두 개다. <ruby>세그먼트 컨트롤<rt lang="en">Segmented Control</rt></ruby>도 같은 방식이다.
선택지를 나란히 두고 현재 쪽을 강조하면, 버튼이 현재인지 미래인지 고민할 이유 자체가 사라진다. 대신 자리를 더 차지한다.

## 스크린 리더에 상태를 알리는 두 가지 방법

화면을 보지 않고 스크린 리더로 듣는 사용자에게도 같은 질문이 생긴다.
아이콘 버튼도 스크린 리더에는 이름(`aria-label`)으로 읽히므로, 화면에서 그림으로 표현한 것을 코드에서는 이름과 상태로 표현해야 한다.
방법은 두 가지이고 그 가운데 하나를 고른다.

- **현재 상태 방식:** 이름은 `음소거`로 고정하고, 켜짐·꺼짐은 `aria-pressed="true|false"`로 알린다.
  스크린 리더는 "음소거, 토글 버튼, 눌림"처럼 이름과 상태를 따로 읽어 준다.
- **미래 동작 방식:** `aria-pressed` 없이 이름 자체를 `재생하기` ↔ `일시정지하기`로 바꾼다. 코드에서는 토글 버튼이 아닌 평범한 버튼이고, 이름이 곧 누르면 할 일이다.

둘을 섞으면 안 된다. 이름을 `일시정지하기`로 바꾸면서 `aria-pressed="true"`까지 붙이면
"일시정지하기, 눌림"으로 읽혀서, 이미 일시정지를 누른 건지 누르면 일시정지되는 건지 알 수 없게 된다.
[WAI-ARIA 버튼 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/button/)도 토글 버튼의 이름은 상태가 바뀔 때 바꾸지 말라고 한다.
이름을 '음소거'에서 '음소거 해제'로 바꾸는 디자인이라면 `aria-pressed`는 필요 없다고 덧붙인다.

```html
<!-- 
  현재 상태 방식
   - 이름 고정: aria-label="음소거" 
   - 상태 속성 aria-pressed="true || false"
-->
<button type="button" aria-label="음소거" aria-pressed="true">
  <svg aria-hidden="true">…</svg>
</button>

<!-- 
  미래 동작 방식
    - aria-label="재생하기 || 일시정지하기"
    - aria-pressed 사용 금지
-->
<button type="button" aria-label="재생하기">
  <svg aria-hidden="true">…</svg>
</button>
```

## 맺으며

버튼 표현에 절대적인 정답은 없을지도 모른다. 하지만 물어볼 순서는 정할 수 있다.

1. 버튼 밖에서 현재 상태를 알 수 있는가?
1. 반대 상태가 뻔한가?
1. 상태를 빨리 확인하고 바꿔야 하는가?

셋 다 문제없다면 버튼은 누르면 일어날 일을 표현하면 된다. 하나라도 걸린다면 현재 상태를 표현할 자리를 따로 마련한다. 닐슨의 첫 번째 휴리스틱이 요구하는 것도 결국 이것이다.
지금 어떤 상태인지는 사용자가 따져 보지 않아도 보여야 한다.

> **사용자가 버튼 앞에서 잠깐이라도 멈칫한다면, 그 표현은 다시 볼 필요가 있다.**

현재 상태를 표현하든 미래의 동작을 표현하든, 사용자는 누르기 전에
지금 어떤 상태이고 누르면 무엇이 달라지는지 확신할 수 있어야 한다.
